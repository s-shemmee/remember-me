# Data model (Supabase)

All tables live in `public`, have RLS **enabled**, and use `uuid` keys (`gen_random_uuid()`), `created_at timestamptz default now()`. `owner_id` always references `profiles.id`, which equals `auth.users.id`.

## Tables

**profiles**: one per user, created by a trigger on `auth.users` insert.
`id uuid pk → auth.users`, `first_name`, `last_name`, `handle citext unique`, `birthday_day smallint`, `birthday_month smallint`, `birth_year smallint null` (private, never exposed to others), `city`, `bio`, `avatar_kind enum('initials','photo','character')`, `avatar_color text` (pastel name), `avatar_character text`, `avatar_path text`, `timezone text default 'Africa/Casablanca'`.
Built (M1, `…_profiles.sql`): trigger `on_auth_user_created` → `handle_new_user()` (security definer, `search_path = ''`, not callable through the API) sets `first_name` from the sign-up form, else Google's `given_name`, else the first word of `full_name`; it may be null and onboarding asks again. `handle` is null until onboarding (`^[A-Za-z0-9_]{3,30}$`, unique ignoring case). Birthday checks: day and month together, a real date (29 Feb allowed), `birth_year` only with a birthday. RLS: read and update own row only; no insert (trigger only) and no delete (M5). Column grants: `anon` nothing; `authenticated` can't change `id` or `created_at`. Since `…_name_limits_and_relation_colours.sql`: `first_name` 1–40 (was 50), and the trigger cuts longer names to 40.
Built (M5 part 1, `…_profile_settings_in_memory.sql`): `share_birthday bool default true` (off: `my_friends()` returns no date), `theme` (`light` | `dark` | `system`), and a check that `avatar_path` is in your own folder of the private `avatars` bucket. `people.in_memory` (gentle wording for all their days). `notices.actor_id` (who a note is about; goes with that account). Server only: `prepare_account_deletion(user)` (used by the `delete-account` Edge Function before deleting the auth user). `can_view_avatar(name)` for the avatar Storage policy; `my_friends()` and `my_connections()` also return `avatar_path`. Tests: `supabase/tests/profile_settings.test.sql`.

**people**: someone you remember (they may or may not use the app).
`id`, `owner_id`, `name`, `relation text`, `group enum('family','friends','work','other')`, `color text`, `linked_profile_id uuid null → profiles` (set when connected), `little_things text[] default '{}'`, `archived_at null`.
Built (M1 part 2, `…_onboarding.sql`, pulled forward from M2): `name` 1–40 (was 80; `…_name_limits_and_relation_colours.sql`), `relation` ≤ 40, `group` enum `person_group`, `color` one of the six pastels (default `lilac`; onboarding gives the relation's colour, see `docs/design-system.md`), `little_things` ≤ 20, `owner_id` defaults to `auth.uid()`. RLS: owner only for select/insert/update/delete. Column grants: users can't write `owner_id` or `linked_profile_id` (server only, M3).
Since `…_people_editing.sql` (M2 part 1): `relation_kind` is the relation chip (`Best friend`, `Family`, `Partner`, `Friend`, `Colleague`; it sets the default colour and the group), and `relation` is the optional "How you'd describe them" (1–30 characters, e.g. "Little sister"). The app shows `relation` when set, otherwise `relation_kind`. Existing rows were backfilled (chip text moved from `relation` to `relation_kind`). **Removing a person sets `archived_at`** (Undo clears it): archived people are hidden everywhere. Every app query filters `archived_at is null` (index `people_owner_active_idx`), `save_person()` refuses them (`not_found`), and the reminder job (M4) must skip occasions whose person is archived. A job in M4 deletes people archived more than 30 days ago (their occasions go with them, `on delete cascade`).

**occasions**: a day to remember. Belongs to a person, or to the owner themselves (`person_id null`).
`id`, `owner_id`, `person_id null`, `kind enum('birthday','anniversary','graduation','work_milestone','remembrance','other')`, `title`, `day smallint check 1–31`, `month smallint check 1–12`, `year smallint null`, `recurring bool default true`.
Since `…_occasion_kinds_work_and_remembrance.sql` and `…_occasion_repeat_and_titles.sql`: kinds `work_milestone` and `remembrance` (no health kind, on purpose); `recurring` true = every year on day/month, false = once on day/month/year (checks: birthdays always repeat, a once day needs a year; existing graduations with a year were set to once); `title` (≤ 40) is kept for every kind except birthday and required for `other`. Built (M1 part 2): enum `occasion_kind`; `day`/`month` must be a real day of the year (29 Feb allowed), and with a `year` 29 Feb must be a leap year; one `birthday` per person (partial unique index); index on `(month, day)` for reminders. Your own birthday stays on `profiles` (not duplicated as an occasion). RLS: owner only, and inserts/updates may only reference your own people.

**connections**: two users who agreed to see each other's shared things.
Built (M3 part 1, `…_wishlists_and_connections.sql`): `id`, `user_low`, `user_high` (the pair, lower id first, unique: a pair exists once), `created_at`. No status column: "pending" lives on `invites`. Made only by `accept_invite()`, removed only by `remove_connection()` (either side; clears `people.linked_profile_id` on both sides). RLS: either person can read; no direct insert/update/delete.

**invites**: a connection invite by link. `id`, `inviter_id`, `person_id null → people` (invited from a person's profile: linked on accept), `token_hash bytea unique` (SHA-256 of the token; the token itself is never stored, and the hash isn't readable through the API), `created_at`, `expires_at` (+7 days), `used_at`, `used_by`, `revoked_at`. Works once; at most 20 active (not used, revoked or expired) per person. RLS: the inviter reads their own (all columns except the hash); writes only through functions.
`id`, `requester_id`, `addressee_id`, `status enum('pending','accepted','declined')`, unique on the unordered pair.

**wishlists**: `id`, `owner_id`, `title`, `kind enum('birthday','treat','other')`, `visibility enum('private','connections','selected')`.
Built (M3 part 1): two fixed lists per person, created by a trigger on `profiles` (and backfilled): "My birthday" (`connections`) and "Treat yourself" (`private`; a check keeps it private). Users can't create, rename or delete lists yet. RLS: owner read only. Connections read the "My birthday" list's wishes only through `friend_wishes()` (M3 part 2).
**wishlist_shares**: `wishlist_id`, `profile_id` (used when visibility = selected).
**wishes**: `id`, `wishlist_id`, `title`, `price_amount numeric null`, `currency char(3) default 'MAD'`, `url text null`, `image_path null`, `emoji null`, `note null`, `position int`.
Built (M3 part 1): `owner_id`, `title` 1–80, `url` http(s) only (≤ 2048), `price_amount` ≥ 0, `currency` MAD/EUR/USD/GBP, `note` ≤ 280, `priority enum('love','like','nice')` (Love it / Like it / Nice to have), `image_path` (`<owner id>/<random>.webp|jpg`), `position`, `removed_at` (Undo; an M4 job deletes them with their image). No `emoji` column (a 🎁 tile shows without a photo). RLS: owner only; inserts/updates must use your own list and an image from your own folder. `reorder_wishes(list, ids[])` sets a new order in one go.
**reservations**: `wish_id pk → wishes`, `reserver_id`, `created_at`. One reservation per wish.
Built (M3 part 2, `…_reservations.sql`): plus `cancelled_at` (the owner removed the wish or made it private; restoring within 10 minutes clears it, after that it's final and an M4 job deletes the row; cancelled counts as free). RLS: only the reserver reads or deletes their row; no direct insert or update (`reserve_wish()`). Not in any realtime publication. Removing a connection deletes reservations both ways.
**notices**: quiet in-app notes. `id`, `user_id`, `kind ('wish_removed')`, `actor_name` (copied when made), `wish_id null → wishes (set null)`, `created_at`, `read_at`. RLS: read and dismiss (`read_at`) your own; written only by the `wishes` trigger.

**plans** + **plan_steps**: per occasion per year. Steps: `gift`, `reserve`, `wish`, `celebrate`, or custom (Celebrate Me checklist). `done bool`.

**reminder_settings**: `profile_id pk`, `offsets_days int[] default '{7,1,0}'`, `send_time time default '09:00'`, `email bool default true`, `push bool default false`, `remind_my_people bool default true`.
Built (M1 part 2; 14 added in `…_onboarding_reminders_and_push.sql`): `offsets_days` limited to 14/7/3/1/0 (default `{7,1,0}`), `send_time` 09:00, `email` on, `push` off, `remind_my_people` on. RLS: owner select/insert/update; no delete (goes with the profile). `profiles.onboarded_at` is null until `complete_onboarding()` finishes.
**push_subscriptions**: `id`, `profile_id`, `endpoint unique`, `p256dh`, `auth`, `user_agent`.
Built (M4 part 2, `…_push_notifications.sql`): `device_label` (e.g. "Chrome on Android") instead of `user_agent`, `created_at`, `last_used_at`. Endpoints must pass `is_push_endpoint()` (https, known push services). RLS: read (not the keys) and remove your own; added only through `save_push_subscription()`; no updates. Goes with the profile (cascade). `notification_log.channel` is now used for `push` too.
**notification_log**: `id`, `profile_id`, `occasion_id`, `offset_days`, `occurs_on date`, `channel`, `sent_at`.
Built (M4 part 1, `…_email_reminders.sql`): plus `kind` (`reminder` | `test`), `status` (`claimed` | `sent` | `failed`), `batch_id` (one email; the Resend idempotency key), `attempts`, `provider_id`, `claimed_at`, `created_at`. Unique on `(profile_id, occasion_id, offset_days, occurs_on, channel)` for reminders. RLS: read your own; writes only through the server functions below. Rows go with their occasion; the clean-up drops rows older than 400 days. Unique on `(occasion_id, offset_days, occurs_on, channel)` so a reminder is never sent twice.

**future_notes**: `id`, `profile_id`, `body text`, `opens_on date`. Readable by the owner only, and only on/after `opens_on` (enforce in the policy).
**memories**: `id`, `profile_id`, `year`, `title`, `body`, `image_path`.

**ai_usage**: `id`, `profile_id`, `feature`, `model`, `input_tokens`, `output_tokens`, `cost_usd numeric`, `created_at`. Used for per-user daily limits.
**embeddings** (Phase 3): `id`, `owner_id`, `source_type enum('person','wish','memory')`, `source_id`, `content text`, `embedding vector(N)` (N = the embedding model's dimension), HNSW index.

## RLS rules (write a test for each)
- Owners can do everything on their own rows (`owner_id = auth.uid()`).
- Connected users can read a person's **shared** wishlists and wishes (`visibility = 'connections'`, or `selected` and listed in `wishlist_shares`).
- `reservations`: the **reserver** reads and deletes their own; reserving goes through `reserve_wish()`. Other connected friends see *that* a wish is taken (`friend_wishes()` status `taken`), never who. The **wishlist owner never learns anything**: they can't read `reservations` rows on their wishes, `friend_wishes()` never returns their own wishes, and `reserve_wish()` answers `wish_not_found` for them. (Built M3 part 2; tests in `supabase/tests/reservations.test.sql`.)
- `profiles`: others see `first_name`, `handle`, `avatar_*`, `birthday_day/month` only if connected and allowed by privacy settings; never `birth_year`, `timezone`, email.
- `future_notes`: owner only, and `select` only when `current_date >= opens_on`.
- `ai_usage`, `notification_log`, `push_subscriptions`: owner read; writes only from Edge Functions (service role, server side).

## Functions
- Connections (M3 part 1, all `security definer` with `search_path = ''`, checked against `auth.uid()`): `create_invite(p_person_id?) returns text` (the token, shown once; `too_many_invites`, `person_not_found`, `already_connected`), `invite_preview(p_token)` (anon too: only the inviter's first name and `valid | expired | used | revoked | not_found | own | connected`), `accept_invite(p_token)` (`invite_not_found | invite_expired | invite_used | invite_revoked | own_invite | already_connected`; marks it used, connects, links the invited-from person), `revoke_invite(id)`, `my_connections()` (first name and look only, never birth year, timezone or email, plus which of your people they are), `link_person(person, profile)` / `unlink_person(person)` (one person per connection), `remove_connection(id)`. Tests: `supabase/tests/connections.test.sql`, `wishlists.test.sql`.
- Reservations (M3 part 2, all `security definer` with `search_path = ''`): `reserve_wish(wish)` (`wish_not_found` for anything you can't reserve, including your own; `already_taken` when someone else holds it; reserving your own reservation again does nothing), `friend_wishes()` (your connections' live "My birthday" wishes with `status` free / mine / taken), `my_friends()` (connections with first name, look, your name for them, birthday day and month, never the year), `can_view_wish_image(name)` (for the Storage policy). Internal only (not granted): `are_connected(a, b)`, `wish_is_shared(list)`, `name_for(viewer, profile)`, and the `wishes` trigger function `wishes_reservations_sync()`. `remove_connection()` now also deletes reservations both ways.
- `health_check()`: `returns boolean`, `security invoker`, reads no data. Executable by `anon` and `authenticated` only. Used by `GET /api/health`.
- `save_person(p_id?, p_name, p_relation_kind, p_relation?, p_color?, p_birthday_day, p_birthday_month, p_birthday_year?, p_little_things? = {}, p_days? = []) returns uuid`: `security invoker` (RLS applies), one transaction. Adds a person (`p_id` null) or edits one of yours that isn't archived (someone else's or an archived one raises `P0002 not_found`, so it never reveals whether an id exists). Saves the name (1–40), relation chip and description (≤ 30), colour (default: the relation's colour), group (from the chip: Family / Partner → family, Colleague → work, else friends), little things (trimmed, empty ones dropped, ≤ 20 of 1–60 characters) and the birthday (required, year not in the future, 29 February only in a leap year). `p_days` is a JSON array (≤ 10) of `{id?, kind: anniversary | graduation | work_milestone | remembrance | other, title?, day, month, year?, recurring?}`: rows with an `id` are edited (ids stay stable for `notification_log`), rows without are added, missing ones are deleted; titles (≤ 40) are kept and optional except for `other`; `recurring` defaults to false for graduation and other, true for the rest, and false needs a year; an id from another person is refused. Errors: errcode `22023` with `invalid_name`, `invalid_relation`, `invalid_color`, `invalid_little_things`, `invalid_birthday`, `invalid_days`; `42501` `not_authenticated`. Executable by `authenticated` only. Tests: `supabase/tests/people.test.sql`.
- `complete_onboarding(p_first_name, p_birthday_day, p_birthday_month, p_birth_year?, p_avatar_kind?, p_avatar_color?, p_avatar_character?, p_avatar_path?, p_person_name?, p_person_relation?, p_person_color?, p_person_birthday_day?, p_person_birthday_month?, p_person_birthday_year?, p_person_little_thing?, p_reminder_offsets? = {7,1,0}, p_reminder_email? = true, p_reminder_push? = false, p_timezone?, p_person_description?) returns uuid`: `security invoker` (RLS applies), one transaction. Saves your name, birthday and look, the first person and their birthday (no name = skipped, returns null), reminder settings, then `onboarded_at`. Refuses a second call (`already_onboarded`). Offsets are de-duplicated and sorted, longest first. Names up to 40 characters. `p_person_relation` is the chip (saved in `relation_kind`; anything but the five chips is `invalid_person`), `p_person_description` the optional "How you'd describe them" (≤ 30, saved in `relation`), the little thing ≤ 60 characters. No `p_person_color`: the relation's colour (Best friend rose, Family sky, Partner peach, Friend lilac, Colleague mint, else lilac). Relation → group: Family / Partner → family, Colleague → work, Best friend / Friend → friends, else other. Errors: errcode `22023` with a code as the message (`invalid_first_name`, `invalid_birthday`, `invalid_birth_year`, `invalid_timezone`, `invalid_avatar`, `person_name_required`, `invalid_person`, `invalid_person_birthday`, `invalid_reminders`, `already_onboarded`); `42501` `not_authenticated`. Executable by `authenticated` only.

## Storage buckets (private, signed URLs)
`avatars` (2 MB, images only), `wish-images` (2 MB), `memories` (5 MB). Path prefix = `auth.uid()`; policies check the prefix.
Built (M3 part 1): `wish-images`, private, 2 MB, JPEG/PNG/WebP. Policies on `storage.objects`: read, upload, update and delete only under your own folder. Served with signed URLs (1 hour) made on the server. Photos are shrunk to 1600px and re-encoded in the browser before upload, so EXIF/GPS never leaves the device (e2e test). Since part 2, connections can read (and so sign) the image of a wish they can see: the policy calls `can_view_wish_image(name)`, which checks the wish is live, on a shared list, and its owner is connected to you.

## Jobs
- `pg_cron` every 15 minutes → `public.call_edge_function('send-reminders')` → Edge Function `send-reminders` (pg_net, `Authorization: Bearer <CRON_SECRET>`; the project URL and secret come from Vault: `project_url`, `cron_secret`). Built in M4 part 1 (email; push in part 2). Logic: `src/features/reminders/due.ts` and `run.ts`; server functions (service role only): `reminder_candidates()`, `reminder_log_keys()`, `claim_reminders(profile, batch, keys)`, `reclaim_stuck_reminders()`, `finish_reminders(batch, provider_id)`, `release_reminders(batch)`, `allow_test_email(profile)`.
- `pg_cron` daily at 02:30 UTC → Edge Function `daily-cleanup` → `run_cleanup()` (people archived > 30 days, final cancelled reservations, wishes removed > 30 days, invites past expiry, log rows > 400 days), then the deleted wishes' photos via the Storage API.
- Edge Functions `send-test-email` and `send-test-push` (the user's own token; 3 an hour each, `allow_test(profile, channel)`) and `unsubscribe` (signed token; RFC 8058 one-click).
- Push (M4 part 2): `reminder_candidates()` also returns push-only users with `email_on` / `push_on`; `reminder_push_devices()` lists devices of users with push on (server only); `claim_reminders(…, channel)`, `reminder_log_keys()` and `reclaim_stuck_reminders()` are per channel. `save_push_subscription(endpoint, p256dh, auth, label)` (signed-in user; moves a shared device to its new owner; turns push on).
- Edge Function `link-preview`: fetches a product URL server side (SSRF-safe), extracts title/price/image.
- Nightly: clean expired push subscriptions; remind connected people about your day if `remind_my_people`.

## Dates
`src/lib/dates.ts` owns: next occurrence of `day/month` from today in a timezone, days until, 29 Feb → 28 Feb in non-leap years, age from optional year. Unit-test all of it.
Built (M2 part 1): plain calendar dates only (`{year, month, day}`), so daylight saving and the server's timezone never shift a day. `todayIn(timeZone)` (falls back to Africa/Casablanca), `nextOccurrence`, `daysUntil`, `daysBetween`, `yearsOn` (age or anniversary years, null without a year), `countdownLabel` ("today", "tomorrow", "in N days" up to 45, then "in N months"), `formatLongDate` ("Fri, 6 November"), `formatShortDate` ("Sun, 22 Nov"), `formatDayMonth`, plus `isLeapYear`, `isRealDayMonth` and `MONTHS`. Tests: `src/lib/dates.test.ts`.
Added in M2 part 2: `hourIn(timeZone)` (the greeting), `addDays`, `addMonths`, `weekdayIndex` (Monday = 0), `weekdayName`, `formatFullDate` ("Wednesday 4 November"), `sameDate`, `toIsoDate` / `fromIsoDate` (URLs). A graduation with a year is a one-off (see `src/features/days/days.ts`); the reminder job (M4) must follow the same rule.
